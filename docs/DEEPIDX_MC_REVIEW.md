후속 작업에서 Codex PreToolUse와 Hermes pre_tool_call을 신규 등록하고 Devin 게이트를
교체했다. 새 호스트 실행 및 신뢰 검증은 [현재 적용 기록](MC_HOST_ROUTING.md)을 따른다.
기존 실행 프로세스가 보관한 등록/플러그인은 새 세션에서 로드해야 한다.

## 실제 동작과 오해하기 쉬운 부분

- 훅이 있는 LLM이라고 모두 같은 기능이 생기지는 않는다. 모델 이름보다 **호스트가 어떤 이벤트와 도구 입력 변경을 지원하는지**가 중요하다.
- `Ran`은 실행 UI 표시다. Grafly 사용 여부는 실제 명령과 `grafly tool_output` receipt로 확인한다. MCP는 이 CLI 경로에 필요하지 않다.
- 새 파일은 다음 구조 갱신/조회 또는 Deep에서 반영된다. 모든 호스트에서 파일 생성 즉시 감시하는 공통 watcher는 설치되어 있지 않다.
- `grafly ask`는 순위가 있는 제한된 결과이고 `grafly grep`는 인덱스 범위의 검색이다. 저장소 전체 `rg`와 의미가 같지 않다. 인덱스 밖 파일은 별도 탐색이 필요하다.
- 토큰 절감 footer는 전체 파일 읽기와 비교한 **추정치**이며 과금 내역이 아니다. 자동 노출은 호스트의 종료 훅/출력 지원에 달려 있다.

## 강제 변환의 구체적인 방법

| 호스트 | 지원 경로 | 제한 |
| --- | --- | --- |
| Codex | `PreToolUse`의 `updatedInput` | 설치 및 실제 변환 확인. 이미 승인 질문이 꺼진 모드에만 allow 반환. |
| Hermes | 플러그인의 `pre_tool_call` → `action: modify`, `args` | 실제 플러그인/터미널 검증 통과. 후속 승인/차단 흐름 유지. |
| Devin | `PreToolUse`의 `updatedInput` | 새 CLI 검증 통과. 이전 첫 읽기 차단 게이트 제거. |

일반 명령의 **argv를 보존할 수 있을 때** `grafly run -- <실행파일> <인자>`로 감싼다.
복합 shell 문자열에 정규식으로 접두사만 붙이면 quoting, pipe, exit code, 권한 검사 의미가
달라질 수 있다. TTY/대화형 명령은 분리해야 한다. 검색/읽기 도구 이름 자체를 바꾸는 것은
인자 수정만으로 해결되지 않는다. 이번 설치에서는 전용 Read/Grep을 차단하지 않는다.
모든 실행을 무조건 allow하지 않으며 지원하지 않는 명령은 호스트에 그대로 전달한다.

공식 근거: [Codex hooks](https://learn.chatgpt.com/docs/hooks),
[Claude Code hooks](https://code.claude.com/docs/en/hooks).

## MC 성장과 관계 판정

코드 관계가 전부 `judge.js`에서 만들어지는 것은 아니다. 파서/추출기와 이름 해석,
선택적인 LSP가 구조적 관계를 만들고, `judge.js`는 여러 동명 후보 중 어떤 결과를
앞세우거나 보류할지 판단한다. MC `code_relation` 호출은 별도의 선택적 확장 경로다.

이번 채널은 9개 특징의 기존 seed 규칙을 옮긴 것이다. **학습 모델 교체나 정확도 향상을
실증한 변경은 아니다.** 점수도 정답 확률로 해석하지 않는다. Python/JS 비교 63개 입력과
기존 Grafly 회귀 사례는 동작 보존을 확인한다.

MC의 더 넓어진 분석 범위나 빨라진 스캔은 그 분석기를 실제 호출하는 채널에서 효과가 난다.
사용하지 않는 분석기·지도·모델만 갱신하면 다른 플러그인의 판정은 바뀌지 않는다. 반대로
이제 `symbol_disambiguation`의 규칙/아티팩트가 개선되고 해당 버전이 배포되면, 같은 채널을
호출하는 Grafly도 그 개선을 받는 구조다.

권장 비교 지표는 언어·모호성 유형별 정답 관계 집합에서의 정확한 연결률, 잘못 확신한 비율,
보류율, 커버리지, p95 지연이다. 현재 MC 엔진이 모든 문제에서 더 정확하다는 비교 증거는
없으므로 전체 스캔을 매 조회마다 호출하도록 바꾸지 않았다.

## 배포 상태와 순서

현재 Oracle 안정 런타임은 **0.2.1 / runtime API 1 / 실제 제공 채널 tool_output**이다.
다른 채널의 태그가 목록에 있어도 구현 전체가 클라이언트에 배포됐다는 뜻은 아니다.
새 symbol 채널은 현재 로컬 Grafly에 포함된 portable 구현으로 동작한다.

이번 변경으로 클라이언트와 Oracle 검증기는 API 1/2를 함께 지원한다. API 2는 허용 목록
12개 파일에 Python 판정과 portable JS/JSON을 포함하고 서명·해시·경로·버전 검증을 유지한다.
활성화 전에 Python 및 JS smoke 검사를 모두 수행한다. 서명된 런타임에 채널이 있으면
Grafly는 프로세스 시작 시 해당 검증 버전을 고정해서 사용한다.

Oracle 검증기 2개 파일을 백업 후 갱신했고 `mc-releases` 서비스 재시작 및 인증된 동기화를
확인했다. 안정 버전/태그를 새로 발행하거나 이전 버전을 덮어쓰지는 않았다.
로컬 MC 본체 및 feature worktree, Oracle `mc-lanes/{js,cc,py,rest}`에 새 채널을 반영했다.
각 lane의 기존 `session_compact` 등 다른 채널은 유지했다. `/opt/morecoffee`와
`/tmp/mc-clean`은 채널 시스템 이전 버전이므로 새 catalog를 강제로 덮어쓰지 않았다.

다음 안정 발행 전에는 설치된 클라이언트들의 최소 호환 버전을 확인해야 한다. API 1 전용
클라이언트는 API 2를 거부하고 마지막 정상 버전을 유지한다. 이후 패키지 버전 증가 →
main 커밋/푸시 → `mc/v...`, `channel/symbol_disambiguation/v0.1.0` 태그 → 안정 릴리스 →
Oracle 승인/서명 → 클라이언트 SSE 수신/검증/전환 순으로 진행한다. 이번 소스 변경은
아직 커밋/푸시 및 새 안정 릴리스 발행 전이다.

전체 배포가 필요해도 분석기, 공용 규칙/모델, 호스트 어댑터를 별도 버전으로 묶고 호환성을
검증하는 편이 낫다. **프로젝트 소스에서 만든 개인 그래프는 공용 배포물에 포함하지 않는다.**
모델·분석기는 OS/아키텍처/ABI, 용량, 라이선스 및 자원 한도가 추가로 필요하다.

난독화 목적은 사용자가 코드를 분석하는 데 드는 비용을 높이는 것이다. MC 핵심 분석기의
네이티브 컴파일과 디버그/원본 자료 제외, 서명 검증 유지가 권장된다. 이 목표만을 위해
프로젝트 소스를 Oracle로 보내는 구조로 바꿀 필요는 없다. 현재 portable 파일은 난독화된
파일이 아니며 네이티브 배포물 생성은 별도 릴리스 작업이다.
[Nuitka의 데이터 보호 설명](https://nuitka.net/doc/commercial/protect-data-files.html)도
일반 onefile 배포와 내장 데이터 보호를 구분한다.

- 로컬 feature worktree 및 Oracle 4개 lane에서 채널 로딩 검사 각 4개 통과.
- 실제 모델 최초 실행 ready; 변경 없는 재실행 cached; 파일 하나 추가 후 기존 의미 2개 cached,
  새 의미 2개 computed, pending/stale/errors 0. 실제 설치 훅의 서로 다른 2개 세션 완료 확인.
- 전체 테스트 스위트 및 모든 호스트의 새 UI 세션은 실행하지 않았다. 각 테스트 묶음에는 중복 사례가 있다.
- 기존 Oracle 모델 터널 작업을 재시작해 연결을 복구했다. 새 모델 서비스는 설치하지 않았다.
- 업데이트 작업 재시작 때 남아 있던 이전 Node 자식 프로세스를 lock PID와 명령 경로로
  확인해 종료한 뒤 다시 시작했다. 터널과 MC 업데이트 예약 작업 모두 Running을 확인했다.
- 이전 원본은 각 프로젝트 `.grafly/.migration-backups/<id>/index`, 설치 백업/검증 자료는
  `C:/Users/example/.grafly/install-backups/20260922-182310/`에 보관한다. 원본 합계는 약 644 MiB다.
- 이 인덱스 백업에는 자동 만료가 없다. 요청한 **20 MiB는 도구 원문 기록의 별도 예산**이며,
  실행 중 기록 보호 정책도 유지된다. 인덱스 세대 보관량은 별도 정책이 필요하다.
- 검색 출력은 200줄 제한만으로 매우 긴 JSON 한 줄을 제어하지 못하는 사례가 확인됐다.
  원문 receipt는 유지하면서 표시 바이트/줄 길이를 제한하는 개선이 추가로 필요하다.
- 다음 개선 우선순위: 클라이언트 호환 버전별 안정 배포, 실패/미완료 Deep 상태의 호스트 표시,
  일반 승인 모드에서의 비승격 변환 지원, 인덱스 보관 예산, 관계 정확도 비교 데이터.
